# @sessionpipe/core

## 0.13.7

### Patch Changes

- 0c3702a: Pairing a Mac again no longer leaves it with no daemon. Installing the service over one that is running (`sessionpipe control pair` on a machine that is already paired, `sessionpipe ask on`) booted the old one out and bootstrapped the new one at once; launchd answers a bootout before the old process has exited and refuses a bootstrap until it has, so the daemon was stopped and nothing started it again: the machine read offline until someone ran `launchctl bootstrap` by hand. The install now waits for launchd to let go of the old service (up to 10 s) and then starts the new one, and when launchd still refuses, the error says what launchctl answered and the command that starts it. On a Mac this happened to, pair again or run `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/org.sessionpipe.control.plist`.

## 0.13.5

### Patch Changes

- af298b3: An ACP agent that goes away with a message to it still unwritten no longer raises an error nobody catches. A message longer than a pipe holds waits in the pipe; when the agent then exits or is closed, the write fails afterwards, on the agent's input stream, which had no error listener: an uncaught `write EPIPE` in the daemon. The failed write is now heard like the agent's exit is: whoever is waiting for the answer gets "<agent> stopped taking input: …" (or its exit), and the session is closed so the next message opens another.
- 54736f5: A turn that was stopped no longer reads as answered with "No response requested."
  
  When a Claude Code session is resumed after its last turn was ended mid-way (a Stop sent
  through `sessionpipe control`, a killed process, a crash), Claude Code writes "No response
  requested." into the transcript as the assistant's, under its own `<synthetic>` model.
  sessionpipe sent that on as what the agent had said, so a receiver drew a stopped turn as
  answered with those words. It is now read as the end of a turn that was stopped, the way
  `[Request interrupted by user]` is: the turn goes out with what it had really said, which
  may be nothing. Claude Code's other synthetic rows, such as an API error, are still the
  turn's reply.
- 4d1a18e: A Claude Code session is found only under the id its transcript is filed as. On a disk that ignores case (macOS, Windows) a command naming `claude-code:8C132906-…` opened the transcript of `8c132906-…`, while the session's registry row and its hooks, which are what say it is open in a window or mid-turn, are kept under the id as Claude Code wrote it: the session looked idle and was resumed in place, `claude -p --resume 8C132906-…`, beside the person's own window. Such a command is now refused `no_session` ("no Claude Code session 8C132906 on this machine") on every platform, as it already was on Linux. A new session's id that differs from an existing session's only by case is still refused as taken (`bad_session`): on such a disk it would be written into that session's file.

## 0.13.4

### Patch Changes

- 2e80bf1: A message to a session whose headless run has just exited now resumes it in place at once. A transcript written in the last 90 seconds used to count as a session in use whoever wrote it, so a message sent 7, 9 or 39 seconds after a `claude -p` at a terminal had exited ran in a copy, and the reply said the session was open in a window. The session's own end, as its hooks report it (`SessionEnd`), now accounts for that write the way the end of the daemon's own run already did; a write nothing accounts for still makes a copy, since a writer may be behind it. Where a copy is made the ack says why, as the machine found it: `detail` opens "ran in a copy, because" and then "the session was open in Claude Code on this computer (a terminal window or the Claude app)", "another Claude Code process on this computer was running the session", or "the transcript of the session had been written to in the last 90 seconds by a process this computer could not find", followed where it applies by "; it could not be reached in place: …" with what the session's own inbox said. A later message that resumes the copy says "ran in the copy made earlier, because …". The copy itself is told "the original is open in a window" only when it is. The refusals for a held session that can't be copied say the same three things instead of "the session is open".
- 8fb6b5d: Nothing of a message's `id` reaches a session unless it is a whole ULID. The id is the receiver's and nobody signs it, and the last twelve characters of whatever it was went into the text written into a live session's inbox, inside the header that says "signed on the sender's device". This release puts that mark on every message handed to a live session, and makes it only from a 26-character ULID: `messageMark` in `sessionpipe-core/control` answers null for anything else, and `frameMarked` then frames the message without one. A message whose id is not a ULID is still delivered, as far as it can be without a mark. It is not handed to a session's `sessionpipe channel` and not written into its inbox, the two ways in whose only proof of delivery is the mark, so it takes the next rung instead: the session's Stop where a turn is running, else a resume or a copy (a copy's ack says "it could not be reached in place: the receiver gave this message an id that is not a ULID, so the turn it would cause there could not be told from any other"). Handed over at the session's Stop or to `sessionpipe wait`, it is acked `delivered` with no `reply` when the session's turn ends. Receivers that follow HTTP.md already send ULIDs and see no change.
- 04d615f: When the daemon can't read a Claude Code's options, the refusal says why in the command's own words: `claude --help` failed: env: node: No such file or directory (the first line it wrote to stderr), "no such file", "the file can't be run (permission denied)", or its exit code. It used to say only "failed", which gave the person who sent the message nothing to act on. The line is one line of at most 200 characters, with the home folder written `~` and anything shaped like a secret removed.
- d41c1ff: Closing an ACP agent that has already exited signals nothing. The daemon closes a held agent it finds gone, and the close armed its two timers all the same (SIGTERM after 2 seconds, SIGKILL after 12), whose only disarming was an exit that had already happened: both went to the number of a process group that no longer existed, or that the system had since given to another process.
- 489494e: A headless run that reaches its 30-minute cap no longer signals its process group ten seconds after the child has exited. The follow-up SIGKILL was on a timer that was never cleared, so it went to the group's number even when the group was gone: the one way the daemon could signal a process it had not started (a pid reused as a group leader inside those ten seconds). The timer is cleared when the child exits, whatever the child left in its group (a tool that ignores SIGTERM) is killed at that moment, once, and a cap that arrives after the child has exited signals nothing and no longer marks the finished run as timed out. A run ended by a Stop, which this release adds, is ended the same way.
- d9def02: The control daemon builds the words around a delivered message with the same definitions the transcript readers take them off with (`sessionpipe-core/control`), so the three wordings this release adds are left out of a turn's `user` text like the rest: the header that names the message where it is handed to a live session at its Stop or through its waiter (`Message via <host> (sessionpipe control, signed on the sender's device; message XXXXXXXXXXXX):`), the note to a copy whose original is not open in a window but in use by another process, and the mark in an ask handed over in place (`…with sessionpipe ask, message XXXXXXXXXXXX. Answer here in full: …`). The paragraph that says an agent asked stays, in its plain form (`(Asked by <harness>:<id> on this machine with sessionpipe ask. Answer here in full: …)`), whichever way the task arrived. `sessionpipe-core/control` exports `messageMark` (null for an id that is not a ULID), `frameMarked`, `copyNote(why)` and `unframe`, and `frameAsk` takes the mark as a third argument.
- d8523d5: The protocol's JSON Schemas (`schemas/v1/*.json`) are generated from `proto/sessionpipe/v1/*.proto`, the protocol's one definition (RFC 0001, step 1), byte-identical to what the Zod source produced. The Zod file stays this release and is held equal to the proto by a test; nothing on the wire changes.
- ce3f0ab: The reply to a message delivered in place (at a session's Stop, to its waiter, into its inbox) is now the answer to that message, or nothing. Three things went wrong on one day: a message handed over at a Stop came back with the sentence the session had written before the message arrived (Claude Code writes its transcript a moment after the fact, so the turn's last words landed after its Stop hook had asked); a message to a session that also had a copy was read from the copy's transcript, so its ack waited 215 seconds and carried a later message's answer; and another such message was acked 30 minutes late with no reply at all. The message now names itself in its frame, by the last twelve characters of its id (`…signed on the sender's device; message XXXXXXXXXXXX):`, and for an ask `…with sessionpipe ask, message XXXXXXXXXXXX.`), the reply is what the session wrote after the rows its transcript records for that message and before anything else begins (the next message, a prompt the person types, a turn a background task starts), it is read from the transcript of the session the message was handed to, and the final ack goes out when the session's own hooks say that turn ended. Where no answer can be put down to the message the ack is `delivered` without a `reply`, and no longer carries a file path in `detail` when the transcript can't be read.
- 26eec6c: Stop (`cancel`) now stops a turn the daemon itself is running. A session started or resumed from a page runs as a `claude -p` (or `codex exec`, `agy`) child of the daemon, and a Stop for it used to be acked `unsupported` while the turn ran to its end. The daemon now ends that child the way it ends one at the 30-minute cap (SIGTERM to its process group, then SIGKILL to whatever is left, ten seconds later or as the child exits), acks the cancel `taken` and then `delivered` with the turn's mode and "stopped the turn this computer was running for that session", and acks the stopped turn's own message `delivered` with what it had written, ending "(The turn was cancelled.)". A message queued behind the stopped turn still runs next, in order. A turn in a process the daemon did not start is never signalled: the cancel is `unsupported` and says who has the session ("…open in Claude Code on this computer (a terminal window or the Claude app)… press Esc there", or the pid of someone else's headless run), and a session nothing is running in is `expired` ("nothing is running in that session as far as this computer can tell, so there was nothing to stop"). spec/CONTROL.md §6 `cancel` says so, with fixtures `conformance/delivery/30`–`33`.
- 4d9654f: What 0.13.0 to 0.13.2 told a copy ("You are a copy of that session, started to answer this message: …") is taken off a turn's `user` text like the notes written today. No daemon says that sentence any more, but every copy those versions made has it in its transcript after the person's words, where a backfill reads it. Where another agent's task went to such a copy, the paragraph that says who asked is the last of the turn's `user` text, as for any other ask.
- b6ed157: A turn in a Claude Code terminal session reaches a tier-2 sink when it ends, not when the next one does. Claude Code writes its transcript up to 100 ms after the fact and a terminal's Stop hook fires sooner than that, so the worker used to read a file that did not hold the turn's last message yet: the receiver got "the turn ended" and then the prompt and the reply one turn late, or only when the session closed. The Stop names the turn's last words, and the worker now waits for the file to hold them: 400 ms with the turn's end, then for 5 s more behind it, then at the session's next hook. A turn is sent once, and whole: one that said something before a tool call is no longer sent as that half with the rest as a second turn that nobody asked. The hook itself does no more than before.
  
  A turn stopped with Esc or Ctrl-C is no longer lost. No hook fires for it, so at the session's next prompt, compaction, start or end the worker reads the interruption from the transcript and sends the turn with what it had said, and a `turn.ended` with `reason: interrupt` where the turn was still held as running. The next prompt is a turn of its own instead of being joined to the one that was stopped, and `[Request interrupted by user]` is never part of anyone's prompt.
- 59d0716: A turn's `user` text is what the person wrote, and nothing the machine wrote around it. A receiver draws that text as the person's own message, and three things were getting into it from Claude Code sessions. A subagent's report: when a subagent hands its report back, Claude Code records it the way it records a message from another session, and it was read as part of the prompt ("[Subagent hand-back] The text below is the final report of a subagent…"). sessionpipe's own words around a message it delivers: "(Sent via <host> with sessionpipe control, signed on the sender's device.)", "Message via <host> (sessionpipe control, …):", the note to a copy of a session ("You are a copy of that session, started because the original is open in a window…"), and the notes on how an answer travels. And `[Request interrupted by user]`. All are left out now, in `turn.transcript`, in `turn.progress` from its first moment, and in the title a session takes from its first ask; the list of attached files stays. sessionpipe's sentences come off only where the daemon puts them (the line before the words, the line or the note after them): the same words typed or pasted by the person stay, and a prompt that is nothing but one of them is sent as typed.
  
  Two of sessionpipe's own lines stay where they were, because a receiver tells an agent's words from the person's by them: the paragraph after a task another agent asked with `sessionpipe ask` ("(Asked by <harness>:<id> on this machine with sessionpipe ask. …)", the last paragraph of the turn's `user` text however the task arrived), and the first line of a handoff's answer ("Answer from <harness>:<id> (sessionpipe handoff, …):").
  
  A message delivered into a terminal session at a Stop hook is now a turn of its own: its `user` text is the message, marked `injected` like any message that arrived from elsewhere, and the reply is that turn's. Its reply used to be added to the turn before, or sent as a turn with no prompt.
  
  `sessionpipe-core/control` exports the sentences (`frame`, `frameStart`, `frameMarked`, `frameAsk`, `frameHandoff`, `IN_PLACE_ANSWER`, `copyNote`, `RE_ARM`) and `deliveredWords`, which takes off a text the ones that are not the message.

## 0.13.1

### Patch Changes

- 5892379: A config.json that does not parse (a hand edit's trailing comma, a byte-order mark, a file cut short) is no longer written over with the defaults, which erased the machine's name and every sink with its token. A command that would save it stops with an error naming the file and what is wrong with it; `install`, `connect`, `uninstall` and `control pair` stop before they change anything, and `sink add` before it asks the receiver anything. A config.json that is there but cannot be read is not written over either.
- 4eb5a68: Devin: the transcript walk ends at a node it reaches a second time, so a session store whose parent chain loops back on itself no longer hangs the reader.
- 439d8a6: A machine running workflows with hundreds of parallel subagents no longer runs a receiver out of requests (#208). A receiver is now sent a subagent's finished tool calls (`tool.ended`) at most one per session per minute, plus the one that shows a subagent's permission prompt was answered, the main thread's tool events as they happen, and at most one request a second from the machine, carrying everything that piled up meanwhile. Turns, prompts, permission questions, subagents and file changes are never thinned, and the local outbox still keeps every event. `sessionpipe sink add … --tools all|main|beat` picks what a sink is sent: `all` (every tool call, as before) is the default; a receiver that meters requests asks for `main` with `tools` in its well-known file, which the machine reads at `sink add` and `connect` and again once a day; `beat` thins the main thread too. No receiver's view changes on this upgrade unless it asked. `sink list`, `status` and `doctor` show each sink's setting; `replay` says how many tool events it thinned and takes `--tools all` to send every one once. A permission prompt now carries `agent_id` when a subagent asked, and a Codex subagent's tool calls carry one too. A worker near the end of its 15 s life no longer starts a drain it can't finish, and hands the work to a fresh worker instead; two workers can no longer both take over the same stale lock. In a simulated workflow of 100 subagents making 30 tool calls each over three minutes (6,214 events), a receiver got up to 6,214 requests before (one per event, with the jobs run one after another; real concurrent workers merged some) and 76 with the default; a replay of the issue's real events put the same rules at about 9,900 requests a day, against 39,500 with the one-a-second pace alone.
- 2f7f39c: `sessionpipe forget` takes the session out of every sink's cursor along with its outbox file, so a session that goes on after it (still running, or resumed later) is sent from its new file's first event. Before, each cursor kept the old file's end offset, and the sinks read nothing from the new file until it grew past that offset, then started mid-way, so the first events were never sent. The cursors are the drain's, so `forget` and `replay` wait for its lock (up to 10 s) before they change anything; past that they change nothing, say so and exit 1. A cursor file holding `null` or a list reads as empty instead of stopping a drain.
- a0197d5: A harness config file the system won't let sessionpipe write (read-only: EACCES, or EPERM on Windows after `attrib +r`; a read-only filesystem's EROFS) is reported for that one file with the code — `! claude-code: ~/.claude/settings.json — can't write it (EACCES); not touched` — the way a file that is not plain JSON already was, and `install` goes on to the next harness, so Codex and Gemini CLI are still hooked. Before, the first such file ended the whole command with `EACCES: permission denied` and left every harness after it unhooked. The refusal is caught where each file is written, so a file the adapter wrote before it (Codex's hooks.json before config.toml, one Claude Code account's settings.json before another's) keeps its report, `created` included, which `uninstall` needs. `uninstall` reports a file it can't write or delete the same way and goes on. Only a write that fails after the file was opened (ENOSPC) says the file may be cut short instead of "not touched".
- 7295fc9: A session whose outbox file was pruned (untouched for `keep_days`, 30 by default) and then resumed under the same id is sent again. Before, pruning also deleted the session's seq counter but left each sink's cursor at the old file's end, so the resumed session restarted at seq 0, which a receiver's (harness, session, seq) deduplication drops as already seen, and the sinks read nothing from the new, shorter file until it grew past the old offset, then started mid-line. Now the counter stays and each sink's cursor into the pruned file is removed.
- f24d3c2: pii@1 keeps an ISO date: `released 2026-10-31` stays as written instead of becoming `released [phone]`, and `2026-10-31 12:00` no longer becomes `[phone]:00`. A date (years 1900–2099, month 01–12, day 01–31) is kept only when nothing after it could carry the run on: no letter or digit, and no separator then two digits (a phone's group; `2026-10-31 5 files` keeps its date) unless that is a time's hour (` 12:00`, 00–23), and not right after a `)` or a `+` with a country code. A date after a `+` (a diff's added line) is kept too. A date that a phone's digit group follows directly, as in `2026-10-31 415-555-0132` or `2026-10-31 0132:`, is read as before (a `(`, `+` or `,` between them starts a new number, and the date stays).

## 0.13.0

### Minor Changes

- aa44c74: Control: a handoff's `reply_to`, and the events of an ask (CONTROL.md §3.1, §6 *Handoff*, §13; PROTOCOL.md §3, §4). A `prompt` or a `start` MAY carry `reply_to`, `<harness>:<id>` of a session on the same machine that gets the answer as a message once the command's turn ends. `sessionpipe-core/control` accepts it on those two kinds only, as a session ref by the adapter's rule and never the command's own session, and refuses the rest `bad_fields`; the command's acks are unchanged. Two event types on the asking session, `delegation.started` and `delegation.ended` (tier 0; `text` at tier 1, `reply` at tier 2), and one session field, `delegated_by` (from `SESSIONPIPE_ASKED_BY`, read like `launched_by`), say which session asked which and what came back. Schemas: `control-command` gains `reply_to`, `control-hello` and `control-pair` gain `ask` and `handoff`, `event` gains `session.delegated_by`, `event-data` the two types. Five new shared vectors (`165`–`169`). `jobEnv` and `claudeEnv` drop `SESSIONPIPE_LAUNCHED_BY`, `SESSIONPIPE_ASKED_BY` and `SESSIONPIPE_ASK_CHAIN` from the daemon's own environment (`withoutLineage`, `LINEAGE_ENV`), so a child carries exactly the lineage the daemon gives it and nothing the daemon's shell had.
- aedb6e9: Control: an `inbox` delivery mode (CONTROL.md §6.3). A message for a session somebody has open is written into Claude Code's own local inbox for it, so the turn runs in that live process, in the mode the person left it in, in the window or thread they are already looking at — instead of being answered by a copy. It sits between `turn` and `api` on the ladder, is chosen before the first byte (one live registry record in the account the session resolved to, the inbox protocol, an interactive process, a socket of this uid, a matching process start time read in UTC, an idle session, a signed `iat` at most 120 s old, a permission class), and is never retried or re-sent on another mode once a byte is written. The envelope declares THE MACHINE's own permission class, `bypass` only on an `inherit` machine whose account defaults to bypass and may; the mode is used only where that equals the session's own class. A write is confirmed by the row the session writes for the turn it caused, carrying that message's own mark; unconfirmed it acks `failed` with code `held`, says nothing was duplicated, and keeps the mode shut for that session while the message could still be released to it — across a restart of the daemon too, since the hold is kept in its state. Where the session the command named has a copy, all of that is the copy's: its inbox, its hold, its turn. The writer is the daemon's alone: not exported from `sessionpipe-core`, no CLI verb.
  
  Core: `liveRecords`/`liveRecord` read every live session registry row (`liveProcess` is now a question about that list); `findTranscripts` and `resolveHome` pick which Claude Code account a session id belongs to when several hold its transcript, and a message for an id that is filed in two accounts with none of them holding it open is refused `ambiguous_home`. New `hookMode`, `peerClass`, `modeRank`, `CLAUDE_MODES`, `homeSettings`, `NO_HOME_SETTINGS`, `relaunchMode`, `peerAsk`.
  
  Each session's own permission mode is recorded from its hooks (`permission_mode` on every Claude Code payload), in the daemon's own state and no Claude Code home, latest word wins, nothing written when it hasn't changed. A relaunch (`resume`, `fork`) of a session the daemon did not start now re-asserts just the narrowing the session itself chose — `plan` and `dontAsk` always, `acceptEdits` where the account's own default is at least that wide, nothing otherwise, and never `auto` or `bypassPermissions`; a start's own recorded options (#138) are untouched. The ack's `detail` says the mode the new turn recorded, and on an `auto` machine whose Claude Code has auto disabled, that the turn ran in Manual mode.
  
  A copy says so: `CLAUDE_CODE_RESUME_SOURCE_ALIVE` on a fork whose source is still open, a note in the message telling the copy it is one, `copy_of` on the ack, a record with a date and a reason (written beside the plain id map an older daemon reads), a `limits.copies_per_day` cap refused as `copy_limit`, and no copy of a copy. A peer-delivered ask is read as the turn's ask and marked `injected` on `turn.transcript` and `turn.progress`, so a running turn says the same about it as a finished one. `daemon.log` is created 0600, like the files beside it.
- aa44c74: **For receivers.** What a 0.13.0 machine sends and accepts beyond 0.12.0 (CHANGELOG.md, "For receivers (0.13.0)", has the detail).
  
  - **Hello and pairing request** say `ask` (sessions there may ask another agent) and `handoff: true` (a `start` or a `prompt` may carry `reply_to`). A machine that says neither is 0.12.0 or older: send it no `reply_to`, or it refuses the command `bad_fields`.
  - **`reply_to`** on a `start` or a `prompt`: a session on the same machine that gets the answer as a message after the command's final `delivered` ack, framed `Answer from <harness>:<short id> (sessionpipe handoff, asked via <receiver host>):`. The command's own ack is unchanged; the relay is not acked and never relayed further.
  - **Events:** `delegation.started` and `delegation.ended` on the asking session (tier 0; `text` at 1, `reply` at 2), with `relayed` saying how a handoff went, and `session.delegated_by` on every event of the session that answers. Lineage, never authority: join on `to` and `delegated_by`, never read `delegated_by` as a subagent, and keep a `delegation.*` event you don't know as any other type.
  - A receiver that pre-checks commands re-vendors 0.13.0's `sessionpipe-core/control` and its vectors (`165`–`169` are new).

### Patch Changes

- aedb6e9: `sessionpipe channel`: a Claude Code channel, so a message reaches a live session in its own thread. Claude Code runs it as one session's MCP server (`claude mcp add --scope user sessionpipe -- sessionpipe channel`, then `claude --dangerously-load-development-channels server:sessionpipe` while channels are a research preview). It parks on the daemon's local socket as that session's waiter for as long as the session runs, and pushes each message in as a `notifications/claude/channel`: the session takes it in its own permission mode, as the person's own words, and shows it as a message from `sessionpipe` in the terminal and in the Claude app. The daemon routes to it as a waiter while the session is idle and reads the answer back from the transcript. The transcript reader now keeps a channel's message (`origin.kind: "channel"`, wrapped in `<channel source="…">`) as its turn's ask: a turn asked through a channel, Telegram's included, used to reach a receiver with nothing asked.
- b4a0d39: Control: a `claude --help` that couldn't be read is never taken for a Claude Code with no permission modes (#152). `detectCaps` marks a run that times out, or fails without listing `--permission-mode`, as `unread` (and takes a timeout, 30 s by default); `modeFlags` then refuses every level but `inherit`, saying why ("this machine couldn't read its Claude Code's options (`claude --help` timed out after 30 s); try again in a minute"), where it used to refuse `auto` as a mode that Claude Code lacks and to run `safe` with no permission flag at all. The daemon asks an unread `--help` again a minute later, and logs each one, instead of keeping it until a restart. A daemon that started 82 s after a Mac's reboot, beside 28 other Claude Code processes, kept such a read for 8 h 12 min, and refused the message sent in that time.
  
  While that `--help` is unread, the hello offers no Claude Code start at all (an offered `safe` was taken, and then run with no permission flag), and a start is refused before it is taken, never run with an empty argv.
- aedb6e9: In-place delivery with the inbox and the channel together (#159). A job is now claimed by renaming its file and the claim is released only once its events are in the outbox; a sweep gives a claim whose worker is gone back to the queue. A job the session's lock held out used to wait in the queue for the next hook's sweep, however long that took; a fresh worker now starts for it.
- 434d10c: A machine under a flood of hook events no longer floods its sinks. One worker drains the sinks at a time; the others leave their events in the outbox for it and it sends them in full batches of 50, so four busy sessions cost a request per batch, not per event. A sink that answered 429 is not tried again by any worker before its `retry-after`, and one that could not be reached waits 2 s · 10 s · 60 s · 5 min · 30 min, then every 30 min, as HTTP.md §2 has said all along (a machine with four busy sessions was refused 828 times in two minutes and had 5 192 jobs queued, 2026-10-14). The session's lock now covers only the append, not the round trips.
- cdb1dbf: Draining a large session file no longer re-reads the rest of it for every batch: a read takes 1 MB (more only for one event longer than that), not the remaining file up to 8 MB, and counts its offset per line rather than from the start. A 10 MB session drained in batches of 50 decoded 55 MB.
- 67cc4fc: Recover a session's seq counter when its file is empty or not a number (a crash between truncate and write leaves it empty). Before, the counter restarted at 0 and the receiver's deduplication silently dropped every later event of that session; now the next seq is read from the outbox file's last line, as it already was when the counter file was missing.
- dc14f84: `turn.progress`: a message absorbed by a running turn, and text the person never typed, no longer open a turn of their own. Claude Code reports a message sent mid-turn (the person's, another session's, a task notification) as a prompt carrying the running turn's id; its reading went out numbered as the next turn, which the transcript never delivers, so a receiver kept showing it, with an empty reply, instead of the running turn. Such a prompt now leaves the reading on the turn the transcript is in, and a task notification that starts a turn is not shown as its ask. `isInjected` also recognises a wrapper tag with attributes (`<cross-session-message from="…">…</cross-session-message>`).
- cb36e47: The stdout sink answers with a retry result when its writer fails (a closed pipe under `sessionpipe tail | head`), as the file and HTTP sinks do, instead of throwing out of `send()`.
- d4b085c: Stop the transcript cursor before a last line the harness is still writing. Before, a prompt whose line had no newline yet when the worker read the file was counted as read and never delivered, so the reply that followed arrived as a turn with an empty prompt. A complete last line without a trailing newline is still read.
