# Adapters: per-harness mapping

> This document is part of the sessionpipe protocol and is licensed under [CC BY 4.0](LICENSE). The words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119. Status: **Draft** (see [VERSIONING.md](VERSIONING.md)).

An adapter is the only vendor-specific code in sessionpipe: one file under
`packages/core/src/adapters/<name>.ts` plus its fixtures under
`conformance/harness/<name>/`. This document is the registry of harness names and,
per harness, where the hooks are written, which native event maps to which protocol
event, which ids the payload carries, where the transcript is read for tier 2, and the
quirks the code must honour. Every mapping here is proven by a fixture recorded from
a real payload; a row without fixtures is marked *(recording pending)* and is not
yet normative.

**What every adapter reads, and nothing more.** A documented hooks or plugin API,
and files the person's own harness wrote on the person's own machine: the transcript
named in the hook payload, a session registry, the config file's account id (or the
API endpoint its settings name, for a home with no login). No vendor API is called,
no credential is read, no token is sent anywhere. The one exception is the account
pool ([PRIVACY.md §3](PRIVACY.md#3-what-a-sender-never-reads)), which exists only after
the person runs `sessionpipe pool on` or `pool add`, holds only the accounts they added,
and talks only to that vendor's own endpoints for their own requests; the harness's
*Pool* row says exactly what it reads, writes and calls. The
documentation URL per harness is in its row.

**The one exception, the person's own to make.** A harness whose own service names a
session without telling the machine may be asked for that name, and only when the
person turned it on (`sessionpipe titles on`, config.json `remote_titles`; off by
default). The adapter then reads the harness's sign-in on this machine, sends it to
that service alone, for that one read, and keeps it nowhere: never in a file, an event
or a log. Only Claude Code has one (claude.ai, below).

## Common conventions

- **Config written by `sessionpipe install`** is one entry per event, running
  `"<absolute node>" "<absolute dist/hook.js>" <harness> <event>` with quoted absolute
  paths. Never `#!/usr/bin/env node`, never an npx path.
- **stdout**: nothing, except where the harness parses it (Antigravity: `{}`).
- **`session.seq`** is assigned by the sender's outbox, not by the adapter; adapter
  fixtures wildcard it.
- **Facts** (title, url, model, account_id, repo, branch, attended) are read by the worker from
  the harness's files after the hook exits; the hook event itself carries only what
  stdin has. A fixture's `expect` lists what stdin alone yields; `files` in a fixture
  supplies transcripts for fact tests.
- **Ids**: `turn_id` = the harness's prompt/turn id when it has one; `call_id` = its
  tool-use id; `attention_id` = the tool-use id of the permission request when the
  payload has one, else an id the sender mints, unique within the session. Claude
  Code's `PermissionRequest` carries no tool-use id, so its adapter mints
  `perm-<16 hex of sha256(prompt id | tool | input)>`: the same request always names the
  same attention, which is what a `permission.answer` has to name (CONTROL.md §6).
  Notifications without an id are `notif-<epoch ms>`.
- **Who started a turn** (`turn.started.submitted_by`, `turn.started.injected`): only
  `claude-code` fills these today, and only when its payload or the prompt's shape says so.
  `codex`, `gemini-cli` and `devin` leave `submitted_by` absent — no recorded payload of
  theirs names who submitted the prompt — and leave `injected` absent for want of a
  recorded wrapper of their own to key on, not because it is unknowable: all three carry
  the prompt, and Codex's reader already has `codexInjected`. `antigravity`'s `turn.started`
  has no prompt at all. An absent field is unknown, not "the person" (PROTOCOL.md §4).
- **Control** (CONTROL.md §6, §9): only on a machine with control paired, the Stop hook
  asks the daemon's socket for a queued, verified message and may answer a block with
  it, and the PermissionRequest hook may wait there for a verified answer. These two
  are the only hooks that ever print for a harness that doesn't parse stdout, and they
  are exempt from the 150 ms budget.

| Transcript (tier 2) | `<config>/projects/<cwd-slug>/<session_id>.jsonl`; records `type: user\|assistant` with `message.content` a string or text parts, and the person's mid-turn messages: one the running turn absorbs is never a `user` record but `type: attachment` with `attachment.type: queued_command`, `commandMode: prompt` and the text in `attachment.prompt` (a string or text parts); it reaches `turn.transcript` / `turn.progress` as the person's words. Skip `isMeta`, `isSidechain`, non-`human` `origin.kind` (a queued command's is `attachment.origin`, absent in older versions; task notifications and `peer` messages share the record), injected `<tag>…</tag>` blocks — except a `peer` record (an inbox delivery, the words unwrapped from Claude Code's preamble and the envelope) and a `channel` record (the words out of their `<channel>` tag), which are the turn's ask, marked `injected`. **`user` is the person's words, and nothing else.** sessionpipe's own words around a message it delivered are left out, each from the place the daemon puts it and from nowhere else (a person can type or paste the same words, and a prompt that is only one of these sentences is what the person wrote): the line that says where the message came from (before the words for a message into a session that exists, `Message via <host> (sessionpipe control, signed on the sender's device):`, or with the message's own mark where it was handed to a live session in place, `…signed on the sender's device; message <12 characters>):`, CONTROL.md §6 `prompt`; after them for a new session's first, `(Sent via <host> with sessionpipe control, signed on the sender's device.)`), and the one note to the model that may follow the words of a framed message (how the answer goes back; that the session is a copy, in either of its two forms, of an original open in a window or of one in use by another process, or as 0.13.0 to 0.13.2 said it, "…started to answer this message…", which transcripts written then still carry; to start the waiter again). `packages/core/src/control/frames.ts` holds each sentence and takes it off, on a `user` record, a queued command, a `peer` body, a channel's text, the hook's own copy of the prompt for `turn.progress`, and the first ask a session is titled by. The attached-files list stays: it is what the message says. Two of sessionpipe's own lines stay too, because they are the only thing that says the words beside them are an agent's and not the person's, and a receiver tells the two apart by them: the paragraph after the task of a `sessionpipe ask` (CONTROL.md §13), `(Asked by <harness>:<id> on this machine with sessionpipe ask. Answer here in full: …)`, which is the last paragraph of `user` whichever way the task arrived (a session started for it, an idle one resumed, a copy of one, whose note to the copy is taken off after it, or the person's own session at a Stop hook or through its waiter, where no `session.delegated_by` says it; handed over in place the paragraph also names the message, `…with sessionpipe ask, message <12 characters>. Answer here in full: …`, and `user` carries it in the plain form all the same, since the mark says how the task travelled and not whose it is); and the first line of a handoff's answer, `Answer from <harness>:<short id> (sessionpipe handoff, …):`. A subagent's report is never an ask: Claude Code files a hand-back as a `peer` message (`origin.handback: true`, `senderTaskId`, the report in `<agent-message from="<agent id>">`, and its own text says "model output, NOT a message from the user"), as a queued command of the running turn (2.1.322) or as the `user` record of the turn it wakes (2.1.312); both are skipped, and a turn it wakes has an empty `user`. A message sessionpipe's Stop hook delivered (CONTROL.md §6, `turn` mode; the terminal shows it as a Stop hook's error) is a meta `user` record, `Stop hook feedback:` and the hook's reason: where the reason carries sessionpipe's frame it is the ask of a new turn, the frame taken off, marked `injected` like a peer's, so the reply that follows is that turn's and not more of the turn before; any other hook's feedback is skipped. Skipped as before: a tool's result (no text part), system reminders and local commands (`isMeta`, or a `<tag>` block), task notifications (`origin.kind`), compaction summaries (`isCompactSummary`, `repeatsCompactSummary`). Not told apart: a message another Claude session of the same person sent over the same socket without sessionpipe's frame is read as an ask, marked `injected`, as it was (`conformance/transcripts/claude-code/subagent-handback.jsonl`, `copy-of-session.jsonl`, `stop-hook-delivery.jsonl`). **The file lags the hooks.** Claude Code queues its transcript writes and flushes them on a 100 ms timer, and a terminal session (`entrypoint: cli`) fires its Stop within tens of milliseconds of the turn's last message: on 2.1.322 the worker read the file 90 to 135 ms after that row was made and found it in 1 turn end of 9, so a turn reached a receiver when the next one ended. A headless run's Stop comes later (95 to 220 ms after the row) and found it every time. The worker therefore holds a turn to the words its Stop names (`last_assistant_message`): the turn is whole when the last assistant text of the read is those words and no tool call or tool result of the turn follows them, or when a later prompt closed it; until then it is neither sent nor passed over, so a turn that spoke before a tool call is never sent as that half. It re-reads for 400 ms under the session's lock (the `turn.transcript` then sits next to its `turn.ended` in `seq`), then every 100 ms for 5 s without it, then at the session's next hook that is not a tool event, for a minute; the budgets are counted on a clock that only goes forward. Hooks fired close together are handled in the order their workers reach the session's lock, and two cases follow from that. A later hook's worker sends nothing of a turn the hooks still hold as running (the record's `promptId`), unless it was interrupted: that turn is left to its own Stop, so a `turn.transcript` is not sent ahead of its `turn.ended` by the next prompt. A later end handled first (a headless run's Stop and its session's end were 37 ms apart in one recorded run, 179 ms in another) does send it, with every other turn not yet sent; the worker remembers the last turn it sent by prompt id and a digest of its last words, and the Stop that comes after finds its turn gone, sends its `turn.ended` and waits for nothing. A transcript whose records carry no `promptId` (older builds) has neither: there the next prompt's worker may send the turn first, and a late Stop waits out its 5 s. A Stop that names no words (a turn that ended on a tool call or a thinking block), a `StopFailure` and a session's end are read once, as before. **An interrupted turn has no hook.** Esc, or the first Ctrl-C, fires no Stop; Claude Code writes a `user` record whose whole text is `[Request interrupted by user]` (`… for tool use]` when a tool was running). That record is nobody's words and ends the turn as it stands: the turn is sent with what it had said, which may be nothing, and the next prompt is a turn of its own. The worker learns of it at the session's next prompt, compaction or start, where it first sends `turn.ended` with `reason: interrupt` for the turn its hooks still hold as running (matched on the record's `promptId`), and at the session's end, where it sends the turn alone. Nothing runs between an interruption and the next hook, so until then a receiver still holds the turn as running; and the transcript is read only where a sink takes tier 2, so only there is the interruption seen at all (`conformance/transcripts/claude-code/interrupted-turn.jsonl`). |

Asked again a minute later while it has no name, then every half hour, within 3 s (the worker holds the session's lock); a 400, 401 or 404, or no answer, keeps the name it had. | Quirks | Running sessions pick up hook changes live from 2.1.280. `type: "http"` handler exists (native lane). A prompt with pasted images can put the first ask megabytes into the file: stream to it, cap at 16 MB. Every headless run says `CLAUDE_CODE_SESSION_ATTENDED=0`, a Remote Control session included, and only a terminal says `1` (measured on 2.1.307–2.1.310). A `claude -p` started inside a Remote Control session inherits `CLAUDE_CODE_ENVIRONMENT_KIND=bridge` and the bridge owner's ids, but the registry entry it writes for itself has no `bridgeSessionId`: its link, not its environment, tells a Remote Control session from a probe run inside one. **Who started a turn is only partly knowable.** No payload recorded through 2.1.304 carries `source` at all, so `turn.started.submitted_by` is absent on every build in the field today and `injected` is the only signal. `injected` is a **closed list of Claude Code's own wrappers** — `<task-notification>`, `<cross-session-message …>`, `<system-reminder>`, `<local-command-stdout>`, `<command-…>`, closed or self-closing, after trimming — and deliberately narrower than this spec's own transcript reader (`isInjected`), which calls any `<tag>…</tag>` block or HTML comment injected. The reader can afford that: dropping one record from a transcript costs little. A `turn.started` cannot, because a receiver acting on `injected` would drop one of the person's own turns whenever they pasted nothing but an SVG, an HTML page or a JSX element. So `injected` **misses**: a peer message delivered as bare text (byte-identical to a person's prompt), a cron or scheduled wake whose prompt is ordinary text, an HTML-comment injection, and any wrapper Claude Code adds after this list. It is also **not** "no person caused this turn": a Talk or `sessionpipe wait` delivery hands the person's own message over inside a `<task-notification>` whose text is an output-file path. The transcript is no substitute: a queued command's `attachment.origin.kind` is absent in older versions, the transcript fixture records a `<cross-session-message>` with `origin.kind: "human"` and `humanTurn: true` (`conformance/transcripts/claude-code/queued-command.jsonl` line 14), and the hook fires before the record lands. ## Agents driven through ACP (control only)

The [Agent Client Protocol](https://agentclientprotocol.com) (ACP) is one JSON-RPC
conversation over an agent's stdin and stdout, the same for every agent that speaks
it. For control (CONTROL.md §6: `start`, then `prompt` and `cancel` in `api` mode) one
client in the daemon drives all of them; nothing here is a hook adapter, and an agent
in this table reports no events unless it also has a row above. The daemon runs only
an agent that is already installed on the machine: its CLI on `PATH`, or the file
`SESSIONPIPE_ACP_<HARNESS>` names (the harness name upper-cased, `-` as `_`:
`SESSIONPIPE_ACP_GEMINI_CLI`); it never downloads one. The launch line per agent is the
one the [ACP registry](https://github.com/agentclientprotocol/registry) publishes and
checks nightly, as of its 2026-10-22 state (the registry id in the second column); a
harness that has a row above keeps its name here. Claude Code, Codex and Antigravity
have their own drivers (above) and their ACP wrappers (`claude-acp`, `codex-acp`,
`antigravity-acp`) are not run. fx is not in the registry; its launch line is the one
its own manual gives (fx.sh/docs/using-fx/acp, measured against fx 0.0.16 on 2026-11-13).

What the daemon says and reads, in the protocol's own names:

- `initialize` with `protocolVersion: 1`, `clientCapabilities: {fs: {readTextFile: false,
  writeTextFile: false}, terminal: false}` and `clientInfo` naming sessionpipe. An agent
  that answers with `authMethods` and then refuses `session/new` with an *authentication
  required* error is acked `failed` with the agent's words: signing in is done at the
  machine's terminal, never by the daemon.
- `session/new` with `cwd` (the start's folder) and `mcpServers: []`; `session/load`
  with the same and the agent's `sessionId` to reopen one.
  For fx both carry `_meta: {fx: {profileMcpServers: true}}`: an ACP session of fx's
  leaves out the MCP servers in the person's own `~/.fx/mcp.json` unless the client
  asks for them, and a session started from a phone should have what one started at
  the terminal has.
- `session/prompt` with one `text` block; its response's `stopReason` ends the turn.
  The message's pictures (CONTROL.md §6 `start`, **Pictures**) follow it as `image`
  blocks (`mimeType`, `data` in base64, `uri` the saved file's `file://` URL), only to an
  agent whose `initialize` answered `agentCapabilities.promptCapabilities.image: true`
  (agentclientprotocol.com/protocol/initialization: a capability left out is not
  there). The protocol names no type or size, and an agent hands the picture to the
  model it runs, so it is given what the strictest service behind the registry's agents
  takes on every platform, Claude's: a PNG, JPEG, GIF or WebP of at most 3 750 000 bytes
  and 3000 px a side (safe past 20 pictures in a request, which an agent that keeps its
  history reaches), and in one message pictures in order while their base64 together
  stays within 10 000 000 characters (the rest stay in the list). An agent has done
  nothing in the turn until it sends a `text` `agent_message_chunk`, a `tool_call`, or a
  `session/request_permission`; one that answers such a prompt with an error before any
  of those, while the turn is in its time and the process is still there, is sent the
  same message as text alone, once.
- `session/update`: `agent_message_chunk` whose `content` is `text` is the reply;
  `tool_call` and `tool_call_update` name what ran (for the reply's list of refusals);
  every other kind is ignored.
- `session/request_permission`: answered from the machine's mode (CONTROL.md §6).
- `session/cancel` (a notification) for `cancel`.

What the agent's process is given. fx's own default permission mode (`auto`) edits files
and runs the commands it recognises without asking, so fx's process is given its mode
for the machine's (`FX_PERMISSION_MODE`, for that run only, never saved): `ask` on a
`safe` machine, so every call that needs approval reaches `session/request_permission`
and is refused; `auto` on an `auto` machine; nothing on an `inherit` machine, where the
person's own fx setting decides. It wins over a value the daemon's own environment
carries. Every other agent is given nothing for the mode
([control-acp-mode-env.json](../conformance/control-acp-mode-env.json)); a change of
the machine's mode lets go of a held agent (CONTROL.md §6 `start`).

A session an ACP agent runs is placed by the folder its start ran in, which the daemon
records with the agent's session id (`aliases.json`), or by the folder the harness's
own hooks reported where it has a row above.
