The pool: several Claude accounts behind one loopback listener the control daemon runs, so a Claude Code session keeps going when one account's limit is reached. `sessionpipe pool add --import` copies this machine's Claude Code logins into the pool (`--login` signs another account in: a URL, then the code pasted to `--code -`), `pool on` writes the `env` block into every Claude Code `settings.json` and installs the daemon's service if it is missing, `pool` lists the accounts in order with the room each has left, `order`, `enable`, `disable`, `remove` and `refresh` shape the roster, and `pool off` removes exactly what `on` wrote. A request goes to the first account in your order that has room; a session stays on its account while that account has room; the numbers an account reports on a session's request become a tier-1 `limits.observed` with `account_id` on that session, through the outbox like a hook's. Every hello carries the pool (`pool` object), a receiver's signed `pool` command drives it (`on`, `off`, `remove`, `order`, `disable` and `login.complete` need a fresh confirm, never a day grant alone: `confirm_required`), and while the daemon runs the CLI's commands go to it over the local socket, since it holds the listener, the pins and the credentials. The daemon now runs for the pool alone, with no receiver paired, and `control off` keeps its service while the pool is on; `sessionpipe uninstall` runs `pool off` first. Nothing of this happens until you run `pool add` or `pool on` yourself.
