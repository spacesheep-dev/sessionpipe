update: one command leaves the whole computer current

`sessionpipe update` used to update only the copy it ran from and ask the daemon to restart "as soon as nothing is in hand". On a Mac with two copies (the one typed, and another the background service ran) the typed command stayed at an old version while everything looked updated; on a computer where some session is always working the restart never came, and people were told to type `launchctl kickstart`.

Now, when it ends well, the copy you type, the copy the background service runs and the hooks are one version, the newest; the service is running it and has heard from its receivers; and the last line says so. It installs npm's latest into this copy, writes the hooks again from it, puts the service on this copy, and looks that it answers with the new version and has had an answer from each receiver since it started (it waits up to 40 seconds for that, the time a long-poll's first answer can take).

How the service gets onto this copy depends on who runs it. One that launchd or systemd has, and that runs another copy or doesn't answer, is replaced with the safe replace from 0.13.7; it keeps the environment its service file gave it (its PATH, a `SESSIONPIPE_CLAUDE` added by hand), and only the program changes. One whose file is there with nothing running is put back. One that runs this copy restarts itself. One you run yourself (`control pair --no-service`, tmux, a container, WSL without systemd) is asked over its socket to restart itself, and no service is installed that nobody asked for.

When it can't get there it stops with one line that says what is wrong and one that says what to run next: `sessionpipe update` again when npm can't be reached (what needs no download is still done, and nothing is ever moved back to an older release); a `sudo npm install … && sessionpipe update` line for a prefix this user can't write, with the prefix quoted (on Windows: `sessionpipe update` from a terminal opened as administrator); `npx sessionpipe@latest update` for a copy npm didn't install; `sessionpipe control run` where nothing runs the service and there is no service file for it. Where launchd or systemd refuses the new service, the one that was there before is put back and started again, and the command says whether anything answers now.

Exit 0 means everything is current, 3 that the service finishes by itself, 1 that it stopped. A receiver that hasn't answered the service is not a failed update: the last line says the computer is up to date and names the receiver, in yellow, and the exit code is 0. `SESSIONPIPE_NO_UPDATE_CHECK=1 sessionpipe update` changes nothing, as before: it says that updating is off because the variable is set, and how to run it once without it.

A restart is now held back only by what the daemon itself holds: a turn it runs, a message in hand, a permission prompt it holds for an answer, a pooled request being answered. A session someone is working in, mid-turn in its own window, no longer holds it back: that it is mid-turn is written to the daemon's state at a stop and read back at the next start, so a message to it still waits for its Stop. `update` gives the daemon 25 seconds to finish what it holds; past that it says the service restarts by itself when that is done, and there is nothing more to type. Just before it replaces a running service it asks it to stop taking messages, in the same step in which the service is found to hold nothing. A service from before 0.15 does none of this: `update` writes down for the new one which sessions the old one knew to be mid-turn before replacing it, and where the old one restarts itself and waits for those sessions by its own rule, `update` says so and exits 3.

The daemon's own daily update takes the same steps (`installEverywhere`): its own copy, the `sessionpipe` on its PATH when that is another install (the copy a person types), the hooks, then its restart. npm is only ever run on a folder that has `dist/cli.js` and a package.json that says it is sessionpipe. `sessionpipe doctor` sees a split between the three, says which, and names `sessionpipe update` as the one fix; it no longer sends anyone to `sessionpipe install` from an older copy, which was refused or, forced, put the hooks back. Where the service isn't running and there is no service file for it, `doctor` and `update` both name `sessionpipe control run`.

Also: the registry asked for `latest` is the one `npm_config_registry` names, when it names one, since that is where npm installs from. A sessionpipe that keeps its files somewhere other than this computer's usual place (`SESSIONPIPE_STATE`, `SESSIONPIPE_CONFIG`, `XDG_*` or `HOME` point elsewhere: a test, a throwaway world, a profile of your own) never looks at, replaces or stops this computer's usual service, and says so; `SESSIONPIPE_SERVICE_LABEL=org.sessionpipe.<name>` gives it a service of its own, and no other name is taken.

`sessionpipe-core/service`: `serviceState` also answers the program a service file names (`serviceArgv`), and says `manager: null` where launchd or systemd can't be asked from this process; `serviceEnvironment` reads back the environment a service file gives; `installService` restarts a systemd unit that was running onto the new file, and where the manager refuses the new service it puts back the file that was there and starts that one again (`ServiceRefused` says which).
