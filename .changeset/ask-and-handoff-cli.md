`sessionpipe ask <agent|session> "<task>"`: a session hands a task to another agent on this machine and gets the answer on stdout (CONTROL.md §13). The request reaches the daemon on its local socket, never through a receiver. The daemon checks, in order and each with its code, that asking is on, that the agent is one it can run headlessly or a session it can message, the folder allowlist, the depth (A asks B, B may ask C, C may not), loops and the start caps, then runs the ask down the same start, prompt and headless paths a receiver's command takes, at `safe`, or `read` when asked (`--permission`), never wider than the machine's mode whatever it is set to (a session already live keeps its own). The daemon counts depth and loops for itself from the asks it has in hand, under the names it knows the sessions by, and takes three asks at a time per asker and per session asked; a `reply_to` it can't place when the command arrives makes the command no handoff at all (nothing relayed, no event). `ask on` from inside a session is refused unless `--yes`: allowing a folder and installing a service is the person's call. Words after `--` are the task, flags or not. The child's first message is the task and who asked; its environment carries `SESSIONPIPE_ASKED_BY` and `SESSIONPIPE_ASK_CHAIN` (the hook carries the first into the job, an Agent SDK session gets both, and a worker never leaks its own), so the child's events say `delegated_by` and the asker's say `delegation.started` and `delegation.ended`. At the terminal the id and progress go to stderr and the answer alone to stdout, exit 0; a refusal or a failure to stderr, exit 1; a usage error 2; `--json` prints `{ask_id, session, reply, ms}`. A `prompt` or a `start` with `reply_to` is a handoff: after its final `delivered` ack the daemon delivers the reply into that session as a message (§6 *Handoff*), and the events on `reply_to` say whether it was `delivered`, `unsupported` or `failed`. The pairing request and every hello say `ask` and `handoff: true`. `sessionpipe ask on|off|status`: `on` writes `ask: true` into control.json and runs the daemon as a service even with no receiver paired (`control run` serves the socket alone unless asking is off too; `control off` keeps the daemon when asking was turned on by hand); `off` sets it false and removes the service when no receiver remains; `status` prints the switch, the daemon, the agents it can ask and the folders. `sessionpipe ask setup [--remove]` writes a marked section into every Claude Code `CLAUDE.md` and `~/.codex/AGENTS.md` so a session knows the command exists and must never use it to send its own reply; hooks still inject nothing.
