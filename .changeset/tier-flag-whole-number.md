`--tier` takes a whole number: `sink add`, `install --sink`, `connect`, `control pair` and `tail` refuse `--tier` with its value left off, empty, or not written in digits (`--tier one`, `--tier 1.5`, `--tier 0x2`, `--tier --name x`), with "--tier takes 0, 1, 2 or 3", before doing anything. The other `sink`, `install` and `control` subcommands refuse such a `--tier` too, where they ignored it. `connect --tier ""` used to fall back to the default tier and `sink add --tier ""` stored 0; both are refused now. Until now `sink add` stored `--tier one` as `null` (and `--tier 1.5` as 1.5, which no event can carry) and printed "tier NaN sends: undefined", and stored `--tier` with its value left off as tier 0 without a word. A value out of range is still held to 0–3, and a tier of 1.5 already in config.json sends as 1. The hook reads a sink's tier the same way, capped by the receiver's `max_tier` too: a stored 0.5, or a sink a receiver caps at 0, no longer turns every tool event, or every status line's limits, into a job. A sink with no tier in config.json (a hand edit) sends at tier 0, where its events carried `tier: null`, which no receiver takes.
