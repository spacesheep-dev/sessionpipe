A machine running workflows with hundreds of parallel subagents no longer runs a receiver out of requests (#208). A receiver is now sent a subagent's finished tool calls (`tool.ended`) at most one per session per minute, plus the one that shows a subagent's permission prompt was answered, the main thread's tool events as they happen, and at most one request a second from the machine, carrying everything that piled up meanwhile. Turns, prompts, permission questions, subagents and file changes are never thinned, and the local outbox still keeps every event. `sessionpipe sink add … --tools all|main|beat` picks what a sink is sent: `main` is the default for an HTTPS receiver, `all` (every tool call, as before) for a file or stdout sink, `beat` thins the main thread too. `sink list`, `status` and `doctor` show each sink's setting; `replay` says how many tool events it thinned and takes `--tools all` to send every one once. A permission prompt now carries `agent_id` when a subagent asked, and a Codex subagent's tool calls carry one too. A worker near the end of its 15 s life no longer starts a drain it can't finish, and hands the work to a fresh worker instead; two workers can no longer both take over the same stale lock. In a simulated workflow of 100 subagents making 30 tool calls each over three minutes (6,214 events), a receiver got up to 6,214 requests before (one per event, with the jobs run one after another; real concurrent workers merged some) and 76 with the default; a replay of the issue's real events put the same rules at about 9,900 requests a day, against 39,500 with the one-a-second pace alone.
