On Windows the control daemon now keeps running: a scheduled task at your logon, beside launchd and systemd

- `control pair`, `connect`, `pool on` and `ask on` used to end with `no service manager for this platform yet; run sessionpipe control run yourself` on Windows, so the daemon lived as long as the terminal it was started in. They now register a per-user task, `\sessionpipe\org.sessionpipe.control` in Task Scheduler, that starts the daemon when you log on. No administrator is needed: the task is created from a definition with a logon trigger that names you, which Windows lets a standard user do. `control off` removes it, and `--no-service` still leaves it out.
- It opens no window. A task that runs `node.exe` directly opens a terminal window at every logon (measured on Windows 11); the task runs it under `conhost.exe --headless` instead.
- Task Scheduler gives a program no environment, keeps none of its output and restarts it on no exit code, so the task runs a small launcher, `%LOCALAPPDATA%\sessionpipe\service\org.sessionpipe.control.cjs`. It gives the daemon the PATH of the shell that paired, appends its output to `control\daemon.log`, starts it again at once when it exits 75 for an update and after 5 seconds when it fails, and ends when it exits 0. What it runs is one line of JSON in that file, so no path, argument or variable is read by `cmd.exe`. A Node or a profile folder with a `"` or a `%` in its path can't be carried on the task's own command line: pairing says so and installs no task.
- `sessionpipe update` moves the task onto the copy you type, as it does a launchd or systemd service, and the daemon's own daily update restarts through the launcher. `status` and `doctor` no longer say updates on Windows run only while `sessionpipe control run` is running, and `doctor` says when Task Scheduler doesn't have the task. Before it replaces the task, `update` writes down which sessions are mid-turn, as it does for a daemon from before 0.15: replacing a task ends its processes outright, before the daemon can write that down itself. `sessionpipe reinstall` still does not run on Windows.
- A sessionpipe with a service of its own (`SESSIONPIPE_SERVICE_LABEL`) now gives it `APPDATA` and `LOCALAPPDATA` too. On Windows its files are under those, and without them such a service came up on the account's real files.
- `sessionpipe-core/service`: `installService`, `serviceState` and `uninstallService` take `platform: "win32"`; `ServicePlan.manager` and `ServiceState.manager` may be `"schtasks"`; `serviceFiles` also answers the `launcher`; `ServiceSpec.node` names the Node that runs it. The process is told `SESSIONPIPE_SERVICE=schtasks:<pid>`, the pid being the launcher's.
