reinstall: one command that repairs the install, whatever state it is in

Computers end up with several copies of sessionpipe: one typed, another the background service was started from, a third in an npx cache. `update` makes one of them the one in use; nothing removed the rest, and a stale copy first on PATH in some shell started the drift again. And when an install was cut off half-way, there was no command to type at all.

`sessionpipe reinstall` leaves one clean copy of the newest release, in use everywhere, and removes the rest. It shows what it found (every copy, its version, what uses it) and what it will do, a row an action, asks once at a terminal (`--yes` doesn't ask, `--dry-run` only looks, a pipe without `--yes` does nothing), then: fetches the release, has npm install it beside the copy that is there and sees it run (until then nothing is touched: a failed download or install, or a run that is cut off, leaves the computer as it was); swaps the two by renames; writes the hooks again and moves the background service onto it by `update`'s own rules; checks that the copy runs through its link and that typing `sessionpipe` starts it; only then removes every other copy, the one it runs from last. Pairings, settings, keys and the outbox are never touched. It does the whole job in the process that was started, so `npx -y sessionpipe@latest reinstall` is the way in when `sessionpipe` itself no longer runs; `doctor`, a failed `update` and the hooks' launcher say that line. macOS and Linux: on Windows it changes nothing and names `sessionpipe update`.

The one copy lives where the copy lives that typing `sessionpipe` starts, whoever may write there: a second copy is never put beside one that can't be written, and one whole copy of the newest release that is what is typed is "nothing to repair" wherever it is. Where it can't promise that typing ends up starting the one clean copy, it changes nothing and names the one line to run: a file that is not sessionpipe's where the copy's link goes; a copy you type but may not write that is not whole or not the newest (`sudo npm install -g --prefix …`); a file first on PATH that npm did not make (a version manager's shim, a wrapper) when the command was not started through it (no command is named there: none leads out by itself); a checkout or a linked folder as what is typed; a folder that is not provably sessionpipe's where npm keeps the package (what an install that was cut off left: the line moves it aside).

It removes only what is provably a published sessionpipe: a real folder named `node_modules/sessionpipe` in the global folder of a Node this computer has, or in an entry of npm's npx cache, holding nothing a published package doesn't, with a package.json that says so; npm's own `.sessionpipe-XXXXXXXX` leftovers; the link npm made. It deletes these itself, through one function; npm is not asked to uninstall. To look it reads and runs no file it finds (but, for `reinstall`, the one copy you type). A folder is one folder by whatever name it is reached. A checkout, a build, a linked folder, a project's dependency, Volta's copy and a file that only has the name are left and named; a copy that needs `sudo` is left with the one line that removes exactly that folder and its link. A copy in the npx cache that nothing uses is no reason to act and goes with the rest when there is one.

`sessionpipe doctor` has a row for more than one copy (and for a copy that is not whole) and names `sessionpipe reinstall` as the one fix there; it reads the copies and runs none; `doctor --json` gains `copies` and one warning string. Exit codes as `update`: 0, 3 (the service is still at work), 1 (it stopped, or a copy is still there: one next command), 2.

Known limits. Started through a file first on PATH that npm did not make, the copy it runs from is taken to be the one you type, not read: it is brought up to date in place, no other installed copy is removed, and the last line says what is not known. On Windows `reinstall` refuses before it looks: removing folders is not proven there. It has run end to end on macOS; on Linux by its unit tests. From a shell that can't ask the service manager (`su -`, `sudo -u`) while a service file is there, it refuses: run it from your own terminal. With a daemon at work that doesn't say which copy it runs from (one from before 0.15, run by hand), no copy is removed until it is done. `--dry-run` asks npm where it installs, and npm writes its own log for that.

`sessionpipe-core/service`: `serviceState` also answers the process the manager runs for the service (`pid`).
